# Kubernetes Scenario-Based POCs

Focus: mounting and referencing **ConfigMap**, **Secret**, **ServiceAccount**, and **PV/PVC**, plus pod-to-pod communication via a Service. 
Three images are used — build each from its Dockerfile below and push it to Docker Hub or ECR, then reference your own image in every pod spec.

---

## Image 1 — `toolbox` (used in POC 1–8)

General inspection pod used to test ConfigMap/Secret/ServiceAccount/PV/PVC mounts and env vars.

`Dockerfile`:
```dockerfile
FROM alpine:3.20
RUN apk add --no-cache curl busybox-extras
CMD ["sleep", "infinity"]
```

No application code needed — it just idles so you can `kubectl exec` into it.

---

## Image 2 — `inventory-service` (used in POC 9–10)

A small HTTP server that reflects its own environment variables and any mounted ConfigMap/Secret files back in the response — so a `curl` visually proves injection worked, not just an `exec`.

`Dockerfile`:
```dockerfile
FROM python:3.12-alpine
WORKDIR /app
COPY app.py .
EXPOSE 5678
CMD ["python", "app.py"]
```

`app.py`:
python
import os
import http.server

CONFIG_DIR = "/etc/app/config"
SECRET_DIR = "/etc/app/secrets"

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        lines = ["INVENTORY SERVICE", "=================="]
        lines.append(f"APP_ENV env var: {os.environ.get('APP_ENV', '<not set>')}")
        lines.append(f"DB_USERNAME env var: {os.environ.get('DB_USERNAME', '<not set>')}")

        if os.path.isdir(CONFIG_DIR):
            for f in sorted(os.listdir(CONFIG_DIR)):
                path = os.path.join(CONFIG_DIR, f)
                if os.path.isfile(path):
                    with open(path) as fh:
                        lines.append(f"config file {f}: {fh.read().strip()}")

        if os.path.isdir(SECRET_DIR):
            for f in sorted(os.listdir(SECRET_DIR)):
                path = os.path.join(SECRET_DIR, f)
                if os.path.isfile(path):
                    with open(path) as fh:
                        lines.append(f"secret file {f}: {fh.read().strip()}")

        body = "\n".join(lines).encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.end_headers()
        self.wfile.write(body)

http.server.HTTPServer(("0.0.0.0", 5678), Handler).serve_forever()
```

## POC 1 — ConfigMap: Volume Mount + Env Var Reference

1. Create ConfigMap `app-config` with keys: `APP_ENV=production`, `APP_NAME=inventory-service`.
2. Create pod `config-inspector` (`toolbox` image), that:
   - mounts `app-config` as a volume at `/etc/app/config`
   - also injects `APP_ENV` as an environment variable via `configMapKeyRef`
3. Verify:
   - `kubectl exec config-inspector -- cat /etc/app/config/APP_ENV`
   - `kubectl exec config-inspector -- printenv APP_ENV`

Solution:- 

#configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: kube-system
data:
  APP_ENV: production
  APP_NAME: inventory-service

  name: config-inspector

  containers:
    - name: toolbox

## POC 2 — ConfigMap: Mounting a Single Key (subPath)

1. Reuse ConfigMap `app-config` from POC 1.
2. Create pod `config-subpath` (`toolbox` image) that mounts **only** the `APP_NAME` key from `app-config` to the path `/etc/app/name.txt`, using `subPath`.
3. Verify: `kubectl exec config-subpath -- cat /etc/app/name.txt` and `kubectl exec config-subpath -- ls /etc/app`.

**Expected result:** `/etc/app/name.txt` contains `inventory-service`. `ls /etc/app` shows only `name.txt` — `APP_ENV` is not present anywhere in the pod, confirming `subPath` mounts a single key instead of the whole ConfigMap.


subPath: Only mount a specific dir or file in side volume, in our case we are mounting /etc/app/name.txt  … name.txt is a directory

Solution:-

apiVersion: v1

  namespace: kube-system

            configMapKeyRef:
              name: app-config

    - name: app-config

## POC 5 — ServiceAccount: Assignment + Auto-Mounted Volume

1. Create ServiceAccount `app-sa`.
2. Create pod `sa-test` (`toolbox` image) with `serviceAccountName: app-sa`.



3. Verify:
   - `kubectl get pod sa-test -o jsonpath='{.spec.serviceAccountName}'`
   - `kubectl exec sa-test -- ls /var/run/secrets/kubernetes.io/serviceaccount`
   - `kubectl exec sa-test -- cat /var/run/secrets/kubernetes.io/serviceaccount/namespace`

**Expected result:** `spec.serviceAccountName` returns `app-sa`. Without any explicit volume defined in the pod spec, `/var/run/secrets/kubernetes.io/serviceaccount` contains three auto-projected files: `token`, `ca.crt`, and `namespace`. The `namespace` file contains the pod's actual namespace — confirming Kubernetes injects this volume automatically for every ServiceAccount.


A ServiceAccount in Kubernetes is an identity for a Pod/application.
A Kubernetes ServiceAccount (SA) gives a Pod an identity that it can use when communicating with the Kubernetes API.

## POC 7 — PV + PVC: Persistence Across Pod Recreation

1. Create a 1Gi PersistentVolume (hostPath is fine for a local cluster).  -- PV
2. Create a PVC that binds to it.					  -- PVC
3. Create pod `pvc-test` (`toolbox` image), mounting the PVC at `/data`.

4. `kubectl exec pvc-test -- sh -c 'echo hello-from-poc7 > /data/hello.txt'`
5.  Delete pod `pvc-test`. Recreate it with the **same PVC**.
6. `kubectl exec pvc-test -- cat /data/hello.txt`

**Expected result:** `/data/hello.txt` still contains `hello-from-poc7` after the pod is recreated. `kubectl get pvc` shows the claim remains `Bound` throughout, confirming PV/PVC lifecycle is independent of the pod lifecycle.


#pvc-test.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-test
spec:
  containers:
    - name: toolbox
      image: qamre/toolbox:v1
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: shared-storage
          mountPath: /data
  volumes:
    - name: shared-storage
      persistentVolumeClaim:
        claimName: shared-pvc

#shared-pvc.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: poc7-pv

  capacity:
    storage: 1Gi
  accessModes:

## POC 8 — Two Pods Sharing One PVC

1. Reuse (or create another) PVC.
2. Create `pod-a` and `pod-b` (both `toolbox` image), mounting the same PVC at `/data`.
3. `pod-a`: `kubectl exec pod-a -- sh -c 'echo shared-data > /data/test.txt'`
4. `pod-b`: `kubectl exec pod-b -- cat /data/test.txt`

**Expected result:** If both pods land on the same node and the PV is `ReadWriteOnce`, `pod-b` successfully reads `shared-data` — RWO restricts the volume to a single **node**, not a single pod, so co-located pods can share it. If the scheduler places `pod-b` on a different node, the mount fails or the pod stays stuck in `ContainerCreating`, since an RWO volume can't attach to two nodes at once. A `ReadWriteMany` PV (e.g. NFS-backed) would succeed regardless of node placement.


Solutions:-

apiVersion: v1
kind: PersistentVolume
metadata:
  name: poc7-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: poc7-local
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /mnt/data/poc7
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: poc7-local

    requests:
      storage: 1Gi
  volumeName: poc7-pv

## POC 10 — Capstone: order-service + inventory-service, All Four Resource Types
1. ` inventory-service` pod (Image 2):
   - mounts ConfigMap `app-config` as a volume at `/etc/app/config`, and injects `APP_ENV` as an env var
   - mounts Secret `db-credentials` as a volume at `/etc/app/secrets`, and injects `DB_USERNAME` as an env var
   - runs under ServiceAccount `app-sa`
   - mounts a PVC at `/data`

2. ClusterIP Service `inventory-service` targets port `5678`.
3. `order-service` pod (Image 3) gets `INVENTORY_URL=http://inventory-service:5678` from a ConfigMap `order-config`, injected via `configMapKeyRef`.
4. From `order-service`: `curl $INVENTORY_URL`
5. From `inventory-service`: write a file to `/data`, then delete/recreate the `inventory-service` pod (keeping the Service, ConfigMap, Secret, PVC, and 	ServiceAccount bindings identical) and re-verify everything.

**Expected result:**
- `curl $INVENTORY_URL` from `order-service` returns a body containing `config file APP_ENV: production`, `secret file username: <username value>`, and the `APP_ENV`/`DB_USERNAME` env var lines populated.
- `ls /var/run/secrets/kubernetes.io/serviceaccount` on `inventory-service` shows the auto-mounted SA token files.
- The file written to `/data` before deletion is still present after `inventory-service` is recreated.
- `order-service` requires no changes after `inventory-service` is recreated — it only ever referenced the Service name via `INVENTORY_URL`, never a Pod IP.

**Deliverable:** all 3 Dockerfiles + `app.py`, all YAML files, and the exact `kubectl` commands + output that prove each requirement above.
